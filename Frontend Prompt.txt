

You are working on the frontend for a **Hospital Management Information System (HMIS)**.

The Laravel backend/API has already been developed. Your task is to build a **production-quality, comprehensive React frontend** that consumes the hmis backend you have developed.

## 1. IMPORTANT — START WITH API ANALYSIS

Before writing significant frontend code:

1. Read the **entire attached Swagger/OpenAPI JSON**, not just the first few endpoints.
2. Analyze every:

   * API tag/module
   * endpoint
   * HTTP method
   * request parameters
   * request body
   * response structure
   * validation rules
   * authentication requirements
   * authorization/role requirements
   * pagination
   * filtering
   * sorting
   * bulk operations
   * file uploads
   * workflow/state transitions
3. Identify relationships between modules and entities.
4. Identify which endpoints represent:

   * Master data
   * Transactions
   * Clinical workflows
   * Queues
   * Approvals
   * Reports
   * Configuration
   * Administration
5. Create a frontend module map before implementing the UI.

The API documentation states that this is the REST API backend for an HMIS and that the API base path is `/api/v1`. Authentication is based on Laravel Sanctum. Do not invent APIs when an equivalent API already exists in Swagger.

For example, the API contains HR setup/master-data screens, ambulance management and trip workflows, pharmacy prescription/dispensing workflows, radiology prescriptions/results, procurement functionality, etc. These should be represented as coherent frontend modules rather than generic CRUD pages.

# 6. REACT QUERY

Use TanStack React Query as the primary server-state mechanism.

Do NOT put API/server data into Zustand unnecessarily.

For every major resource create appropriate:

```text
useQuery
useMutation
useInfiniteQuery
```

where appropriate.

Use stable query keys.

Example:

```ts
queryKeys.patients.list(filters)
queryKeys.patients.detail(id)
queryKeys.pharmacy.pendingDispense()
```

Implement:

* loading states
* error states
* empty states
* optimistic updates only where safe
* invalidation after mutations
* refetch behavior
* pagination
* filters
* sorting

Avoid manual `useEffect` data fetching.

# 7. ZUSTAND

Use Zustand only for **client/application state**, for example:

* authenticated user/session UI state
* sidebar collapsed state
* selected facility/context if applicable
* UI preferences
* global filters where truly necessary
* modal/drawer state where appropriate

Do NOT duplicate React Query server state in Zustand.

Keep stores small and domain-specific.

# 8. TYPESCRIPT

Everything should be strongly typed.

Create TypeScript types/interfaces corresponding to the Swagger schemas.

Examples:

```ts
interface Patient {
  id: number;
  // ...
}

interface PaginationMeta {
  current_page: number;
  last_page: number;
  per_page: number;
  total: number;
}
```

Do not use:

```ts
any
```

unless absolutely unavoidable due to an undocumented API response, and if that happens isolate it and document why.

Prefer:

```ts
unknown
```

with runtime validation where appropriate.

# 9. API RESPONSE HANDLING

The Laravel API may return different response structures for different endpoints.

Do not blindly assume every endpoint has the same response shape.

Inspect the Swagger documentation carefully and build appropriate response types.

Create reusable utilities for:

* paginated responses
* validation errors
* API errors
* success messages
* file responses
* empty responses

Laravel validation errors such as HTTP `422` must be translated into useful form-level validation messages.

For example:

```text
The selected currency is invalid.
The maximum salary must be greater than the minimum salary.
```

Display errors next to the relevant field whenever possible.

# 10. AUTHENTICATION & AUTHORIZATION

Implement a complete authentication flow based on the actual API documentation.

Requirements:

* Login
* Logout
* Session/user retrieval if supported
* Protected routes
* Authentication persistence according to backend requirements
* 401 handling
* 403 handling
* Permission-aware navigation
* Permission-aware actions

The Swagger documentation includes authorization scenarios where a user may be authenticated but lack a particular screen grant.

For example, the pay-grade API documents a `403` response when the role lacks the relevant screen grant.

Therefore:

**Do not simply hide unauthorized screens visually.**

The frontend should have a proper permission architecture:

```text
PermissionGuard
Can()
usePermission()
```

Example:

```tsx
<Can permission="admin.pay-grades">
  <Button>Create Pay Grade</Button>
</Can>
```

But always treat the backend as the final authority.

* update queue
